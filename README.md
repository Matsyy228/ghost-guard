# GHOST//GUARD

GHOST//GUARD помогает небольшой команде настроить проверку Kotlin-проекта перед релизом и увидеть, какая находка повлияла на решение сценария. Это локальное веб-приложение для кейса «Центр-инвест» на Cyber Garden 2026. Backend запускает связанные блоки и передаёт статусы и данные по мере выполнения. Самописные сканеры проверяют учебные проекты Kotlin/Spring Boot, а итоговый отчёт можно скачать в JSON.

## Установка

1. Установите **Python 3.12 или новее** и откройте папку `хахатон` в VS Code через **File → Open Folder**.
2. Откройте **Terminal → New Terminal** и выполните в PowerShell из корня проекта:

   ```powershell
   py -3 --version
   py -3 -m venv --without-pip .venv
   .\.venv\Scripts\python.exe --version
   ```

   Если `.venv` уже есть и команда проверки версии работает, используйте существующее окружение. Если `py` недоступна, а `python --version` показывает Python 3.12 или новее, создайте окружение командой `python -m venv --without-pip .venv`.
3. Backend использует стандартную библиотеку Python. Frontend использует HTML, CSS и JavaScript. Установка пакетов и сборка не требуются.

## Запуск из терминала VS Code

Обе команды выполняются из корня проекта в отдельных терминалах PowerShell.

**Терминал 1 — backend**

```powershell
.\.venv\Scripts\python.exe -B -u -m backend.server
```

Проверка API доступна по [127.0.0.1:8000/api/health](http://127.0.0.1:8000/api/health). Ожидаемый ответ — `{"status":"ok"}`.

**Терминал 2 — frontend**

```powershell
.\.venv\Scripts\python.exe -B -u -m http.server 5173 --bind 127.0.0.1 --directory frontend
```

Откройте [127.0.0.1:5173](http://127.0.0.1:5173), оставьте источник **Демо** и нажмите **Запустить проверку**. Шаблон выдаст три синтетические находки, по одной от каждого сканера. Оба сервера останавливаются через **Ctrl+C** в своих терминалах.

Те же команды доступны через **Terminal → Run Task → Start app (frontend + backend)**. Перезапускайте backend после изменения Python-кода и обновляйте вкладку браузера после изменения frontend.

## Редактор и проверка ветвления

1. Выберите блок в списке и нажмите **Добавить блок**. Для перемещения зажмите карточку и перетащите её. Для соединения нажмите выход одного блока, потом вход другого. Исходящие связи выбранного блока можно удалить в его настройках.
2. Шаблон содержит ручной запуск, три сканера, условие и два отчёта. Запустите шаблон с **Высокой** минимальной критичностью. Найденный секрет активирует ветку **Да** и её отчёт. Выберите **Критическую** критичность в блоке **Условие** и повторите запуск. В этот раз активируется ветка **Нет**. В отчёте обеих веток сохраняются находки, дошедшие до этого блока.
3. Выберите **Secrets** и нажмите **Удалить блок**. Для сканера с единственным входом и выходом редактор восстановит связь между соседями. Повторите запуск. В отчёте останутся две находки. Кнопка **Вернуть шаблон** восстанавливает исходный граф.
4. Щёлкните по блокам после запуска, чтобы увидеть их статусы, входные находки и результат. Условие проверяет каждую входную находку и выбирает ветку **Да**, если подходит хотя бы одна. Доступны порог критичности, сравнение и регулярное выражение по полю находки. Backend отклоняет циклы и блоки, которые не подключены к ручному запуску.

Редактируемый граф хранится в открытой вкладке. Обновление страницы загружает демошаблон.

## Отладка в VS Code

1. Для backend установите расширения VS Code **Python** и **Python Debugger** через панель **Extensions** или терминал:

   ```powershell
   code --install-extension ms-python.python
   code --install-extension ms-python.debugpy
   ```

   Для frontend используется встроенный отладчик VS Code и Microsoft Edge.
2. Перед запуском отладки остановите серверы, вручную запущенные на портах 8000 и 5173.
3. Поставьте breakpoint в `backend/service.py`, `scan.py` или `frontend/app.js`. В панели **Run and Debug** выберите **Debug app (frontend + backend)** и нажмите **F5**. Backend запустится во встроенном терминале, для frontend запустится задача `Start frontend` и откроется Edge. Нажмите **Запустить проверку**, чтобы дойти до точки останова в обработчике.
4. Для отдельных частей доступны **Debug backend** и **Debug frontend (Edge)**. При отладке только frontend запустите backend первым терминалом. После остановки отладки задача `Start frontend` может оставаться запущенной. Остановите её через **Terminal → Terminate Task**, когда закончите.

## Проверка своего учебного проекта

Выберите **Мой ZIP**, приложите архив проекта организаторов и, при наличии, справочник SCA. Лимиты — 8 МиБ для ZIP и 512 КиБ для JSON. При запуске без справочника SCA отмечается как пропущенный. Архив распаковывается в рабочей папке `.runtime/`, каталог запуска удаляется после обработки.

Полный прогон на наборе «Центр-инвест» описан в [TEST_REPORT.md](./TEST_REPORT.md). Для загрузки используйте ZIP с содержимым `training-project/` в корне архива и официальный `vulnerability-database/vulnerabilities.json` отдельным файлом. SCA учитывает объявленные зависимости, `gradle.properties` и `gradle.lockfile`.

Для встроенного демо также поддерживается короткий формат. Пример записи с вымышленной зависимостью и синтетическим CVE:

```json
[
  {
    "package": "example.training:demo-library",
    "cve": "CVE-2099-12345",
    "severity": "medium",
    "ranges": [{ "min_inclusive": "1.0", "max_exclusive": "2.0" }]
  }
]
```

Сканер также работает из консоли без веб-сервера:

```powershell
.\.venv\Scripts\python.exe -B .\scan.py .\backend\demo\project --catalog .\backend\demo\catalog.json
```

Добавьте `--submission`, чтобы получить JSON по спецификации организаторов. [Пример отчёта на реальном прогоне](./TEST_FINDINGS.json)


## Серверный LLM-блок

Модель объясняет уже найденные проблемы и формулирует исправления по подсказкам сканеров. Backend поддерживает OpenAI-совместимый `/v1/chat/completions` в режиме JSON.

### Qwen2.5-1.5B Instruct на Windows

Для локального запуска понадобятся веса модели GGUF Q4_K_M (1,12 ГБ) и сборка llama.cpp для Windows x64 с Vulkan. Сохраните файл модели в `.runtime/llm/`. Распакуйте сборку `llama-b12248-bin-win-vulkan-x64.zip` в `.runtime/llm/llama-b12248/` рядом с моделью. [Веса Qwen](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/blob/main/qwen2.5-1.5b-instruct-q4_k_m.gguf) · [Сборка llama.cpp b12248](https://github.com/ggml-org/llama.cpp/releases/tag/b12248)

Запустите модель в отдельном терминале VS Code из корня проекта:

```powershell
& .\.runtime\llm\llama-b12248\llama-server.exe `
  --model .\.runtime\llm\qwen2.5-1.5b-instruct-q4_k_m.gguf `
  --host 127.0.0.1 --port 11439 --alias ghost-qwen `
  --ctx-size 4096 --parallel 1 --n-gpu-layers 99 --temp 0 --no-ui
```

Дождитесь `model loaded` в терминале модели. Затем запустите backend в другом терминале PowerShell:

```powershell
$env:GHOST_LLM_BASE_URL = 'http://127.0.0.1:11439/v1'
$env:GHOST_LLM_MODEL = 'ghost-qwen'
.\.venv\Scripts\python.exe -B -u -m backend.server
```

Локальной модели ключ не нужен. Скачанные файлы в `.runtime/` исключены из Git. После загрузки файлов модель работает без интернета.

Для Ollama укажите `http://127.0.0.1:11434/v1` и имя установленной модели. Для удалённого провайдера задайте его HTTPS-адрес API, имя модели и `GHOST_LLM_API_KEY` в окружении сервера. [Документация Ollama](https://docs.ollama.com/api/openai-compatibility)

Запрос к модели содержит ID находки, правило, категорию, критичность, заголовок и подсказку сканера, а при наличии также ID записи из справочника. Сервер берёт файлы и строки из исходного отчёта. За один запрос объясняются до 20 находок, начиная с наиболее критичных.

### Контракт для интерфейса

В JSON графа для существующего `POST /api/workflow` добавьте ноду `{"id":"explain","type":"llm"}` после сканеров или условия. Свяжите её с отчётом. Дополнительных параметров у ноды нет. Как и другие ноды, она возвращает события `running`, затем один итоговый статус.

| Статус ноды | Поля и поведение |
| --- | --- |
| `done` | `output.explanations` содержит проверенные записи. Если они дошли до отчёта, они также есть в `result.report.explanations` |
| `skipped` | `llm-not-configured`, `llm-no-findings` или неактивная ветка. При активной ветке находки продолжают идти дальше |
| `failed` | `llm-config-error`, `llm-provider-error` или `llm-invalid-response` в поле `code`, причина в `message`. Выполнение продолжает формировать отчёт с находками сканеров |

Запись объяснения содержит `finding_id`, `explanation`, `recommendation`, `file`, `line` и, при наличии, `endLine`, `advisoryId`. Для сопоставления с `report.findings` используйте `finding_id` → `id`. При отображении `explanation` и `recommendation` выводите их как обычный текст. Маршрут и формат итоговых находок остаются прежними.
